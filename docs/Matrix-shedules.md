Matrix build with containers

# Proposed YAML (drop-in)

```yaml
version: 0.3

project:
    name: buildfab
    modules: bildfab

vars:
  artefacts_dir: dist
  bin_dir: bin
  build_dir: .build
  build_cleanup: 0
  conan_clenap: 0

# 1) Matrix stage distr.
  distr:
      - action: container-build
        matrix:
          image:
            - "centos:7"
            - "centos:8"
            - "debian:12.7"
          # image: ["centos:7", "rockylinux:8", "ubuntu:22.04"]
        strategy:
            max_parallel: 2     # <- run at most N matrix jobs at once (default: all)
            fail_fast: true     # <- stop scheduling new jobs when any job fails (default: false)
            continue_on_error: false  # <- if true, stage succeeds even if some jobs fail
            # (optional) ordering policy; if omitted, natural order is used
            order: "fifo"       # "fifo" | "random"

# 2) Actions: container,
actions:

  - name: container-build
    description: Build inside ${{ matrix.image }}
    container:
        engine: docker # or "podman"
        image: { from: ${{ matrix.image }} }
        # Optional: build a derived image that has toolchain + buildfab inside
        build:
            dockerfile: "ci/Dockerfile.build"
            context: "."
            args:
            BASE: ${{ matrix.image }}
            # tag will be auto-generated by buildfab (e.g., buildfab/build:centos-7-<hash>)
        workdir: /src
        mounts:
        # Mount your source tree read-only for purity (or read-write if you prefer):
        - type: bind
            source: .
            target: /src
            ro: true
        # A writable output dir on the host for artifacts:
        - type: bind
            source: ./${{ artefacts_dir }}
            target: /out
            ro: false    run_stage: build

        env: # Example: wire an output path env the 'build' stage can use if needed
            ARTEFACTS_DIR: /out

        user: ""                     # root or specific uid:gid; empty = image default
        network: ""                  # default bridge, or "host" if you need
        cache:
        # Optional: ccache dir or buildkit cache mounts
        ccache: /ccache

        # Optional: extra docker run flags in case you need them
        # extra_args: ["--cpus=4", "--memory=6g"]

        # Choose ONE of the two approaches below:
        # --- A) Run the 'build' stage inside the container (cleanest) ---
        run_stage: build # buildfab must be available in container (see below)

        # --- B) (Alternative) Execute a script directly inside the container ---
        # run:
        #   - bash -lc "cmake -S . -B build -DCMAKE_BUILD_TYPE=Release"
        #   - bash -lc "cmake --build build -j"
        #   - bash -lc "cp -r build/* dist/"

```

# Minimal `ci/Dockerfile.build` (toolchain + buildfab inside image)

If you use **`container.run_stage: build`**, the container must have **buildfab** installed so it can execute your YAML inside. You can do it once in a derived image:

```dockerfile
# ci/Dockerfile.build
ARG BASE
FROM ${BASE}

# Example toolchains for typical C++ builds (adjust to each base):
RUN (command -v yum && yum -y update && yum -y install wget curl gcc gcc-c++ make cmake git ccache) || true \
 || (command -v dnf && dnf -y install wget curl  gcc gcc-c++ make cmake git ccache) || true \
 || (command -v apt-get && apt-get update && DEBIAN_FRONTEND=noninteractive apt-get install -y wget curl build-essential cmake git ccache) || true

RUN wget -O - "https://github.com/AlexBurnes/buildfab/releases/latest/download/buildfab-linux-amd64-install.sh" | sh

# Helpful default workdir
WORKDIR /src
```

> If you prefer not to bake `buildfab` into the image, you can **mount** the host’s `buildfab` binary into the container and call it with `run_stage`.

# How the engine should execute this

1. For `distr` stage, **expand `matrix.image`** into N jobs (one per image).
2. For each job:

   * If `image.build` is set, **docker build** a temporary image (tagged).
   * **docker run** with mounts, env, workdir, user.
   * If `container.run_stage` is set → execute:

     ```
     buildfab build
     ```

     inside the container (it reads your same `project.yml` from `/src` mount).
     Otherwise, if `container.run` is a list, execute those commands inside the container shell.
3. Collect artifacts from the mounted `/out` (host `dist/`) and report consolidated status.
4. Run all jobs **in parallel** based on your runner’s `--parallel` setting.

No YAML duplication. The **`build`** stage still defines the steps once. The **`distr`** stage is a pure fan-out driver.

# CLI sugar (optional, useful)

* Run a single image quickly:

  ```bash
  buildfab distr --matrix.image=ubuntu:22.04
  ```
* Override engine defaults:

  ```bash
  buildfab distr --container.engine=podman
  ```
* Limit parallelism:

  ```bash
  buildfab distr --max-parallel=2
  ```

# Artifacts & caching tips

* Use **`ccache`** in the image and mount a host path (e.g., `~/.ccache`) to `/ccache` for speed:

  ```yaml
  mounts:
    - type: bind
      source: ~/.ccache
      target: /ccache
  env:
    CCACHE_DIR: /ccache
  ```
* Prefer **read-only source mount** + a **separate writable out mount** to keep container layers clean and avoid permission surprises.
* If you adopt **BuildKit**, you can add `--mount=type=cache` in Dockerfile steps to share compiler caches between builds.


## Semantics

* **max\_parallel**: scheduler starts up to N matrix jobs concurrently; remaining jobs **queue** and start as slots free up.
* **fail\_fast**:

  * `true`: as soon as any job fails, no *new* jobs are started; in-flight jobs finish; stage then fails.
  * `false` (default): run **all** jobs; stage fails if **any** job failed.
* **continue\_on\_error**:

  * `true`: stage **succeeds** even if some matrix jobs fail (useful for exploratory builds).
  * If both `fail_fast: true` and `continue_on_error: true`, `continue_on_error` wins for final status, but `fail_fast` still stops scheduling new jobs.
* **order**: optional hint for the queue; usually keep `fifo`.

## Interactions & overrides

* **Global CLI cap** still applies: `buildfab distr --max-parallel=3` caps overall parallelism across the whole runner. The effective parallelism is:

  ```
  effective = min(global_max_parallel, matrix.strategy.max_parallel)
  ```
* You can also put a **global default** in top-level `defaults`:

  ```yaml
  defaults:
    matrix:
      strategy:
        max_parallel: 2
        fail_fast: false
  ```

  A stage’s `matrix.strategy` overrides the defaults.

## Logs and summary

* Scheduler prints:

  ```
  [distr] scheduling 3 jobs, max_parallel=2, fail_fast=true
  [distr] started (1/3): centos:7
  [distr] started (2/3): rockylinux:8
  [distr] queued  (3/3): ubuntu:22.04
  ```
* Final summary includes a per-image status table and a stage exit status respecting `continue_on_error`.
